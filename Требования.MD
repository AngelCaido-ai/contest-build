Ниже — разбор требований со скринов и практичный план, чтобы успеть собрать **MVP рекламного маркетплейса в Telegram Mini App + бот**, где сделки идут через **эскроу**, а согласование/переписка — **в текстовом боте**.
## Уточнения по конкурсу и объёму работ

Доставляемый результат — **MVP (рабочий end-to-end прототип)**, а не production-ready система. Для MVP достаточно **одного цельного потока**, например: каталог офферов → создание сделки → аппрувы → оплата/эскроу → автопостинг → подтверждение доставки → release/refund. Часть scope допускается упростить для демо или описать как **дизайн/роадмап**, если **чётко указано, что реализовано, а что — в планах**. Оценка учитывает полноту и качество: чем больше end-to-end покрытие, тем выше балл, но архитектура и качество реализации столь же важны.


## 1) Что именно требуется (чек-лист MVP)

### A. Маркетплейс “двухсторонний”

Должны быть **оба входа**:

1. **Channel owner listings** — владелец канала добавляет канал, задаёт цену/условия, **добавляет бота админом** (для верификации и автопостинга), плюс желательно поддержать “PR-менеджеров” (несколько пользователей могут управлять каналом).
2. **Advertiser requests** — рекламодатель создаёт **заявку/бриф**, а владельцы каналов могут на неё откликаться.

Оба входа обязаны сходиться в **единый workflow**: переговоры → аппрув → эскроу → автопостинг. Сообщения/переговоры — **через текстового бота, не чат внутри мини-аппа**. (([core.telegram.org][1]))

### B. Верифицированная статистика канала “из Telegram”

Автоматически получить и показать метрики, минимум:

* subscribers
* average views / reach
* language charts
* Telegram Premium stats
* другие метрики из Telegram analytics (([core.telegram.org][2]))

**Практическая реальность:** полный набор (языки/графики) официально описан в **Telegram client API (MTProto) stats.getBroadcastStats**. Это не “Bot API”. (([core.telegram.org][2]))

### C. Форматы рекламы и цены

Нужно поддержать цены “по форматам” внутри канала (post/forward/story…), **но для MVP достаточно “post”**. Формат — “свободное поле”, не жёсткий enum.

### D. Эскроу-сделка + жизненный цикл

Поток:
оплата рекламодателем → средства удерживаются платформой → автопостинг подтверждает доставку → release или refund.
Нужны:

* понятные статусы и переходы
* auto-cancel/timeout если зависло
* рекомендация: **отдельный адрес/кошелёк на сделку или пользователя** (кроме hot wallet)

### E. Аппрув креатива + автопостинг + проверка “не удалено/не отредактировано”

Цикл:
бриф → владелец принимает/отклоняет → черновик → ревью рекламодателем → правки → approve → автопубликация в согласованное время → проверка, что пост “доставлен” и живёт достаточно времени → затем выплата.

## 2) Как собрать это в продукт (архитектура)

### Компоненты

1. **Telegram Mini App (UI)**

   * каталог каналов/заявок + фильтры
   * формы: создать listing / создать request / посмотреть deal status
   * кнопки “перейти в бота по сделке”
2. **Telegram Bot (workflow + переговоры + аппрув + уведомления)**

   * один источник “диалога”: кнопки/команды/уведомления
   * принимает файлы/креатив (через file_id), просит аппрув, пишет статусы
3. **Backend API**

   * авторизация пользователя по initData (Mini App)
   * вся бизнес-логика сделок, статусы, права, аудит
4. **Jobs/Queue**

   * таймауты сделок
   * мониторинг оплаты
   * планировщик автопоста
   * пост-проверка “живёт/не изменён”
5. **DB**

   * пользователи, каналы, листинги, заявки, сделки, платежи, события

### Важный дизайн-принцип

**Мини-апп = витрина и формы. Бот = процесс и кнопки.**
Так ты прямо попадаешь в требование “не делать чат внутри мини-аппа”. (([core.telegram.org][1]))

## 3) Модель данных (минимально)

* `User` (tg_user_id, роли advertiser/owner, linkedWallet, createdAt)
* `Channel` (tg_chat_id, @username, title, ownerUserId, botAdminStatus, rightsSnapshot)
* `ChannelManager` (channelId, userId, permissions: pricing/manageDeals/payout)
* `ChannelStats` (channelId, subscribers, viewsPerPost, languagesJson, premiumJson, updatedAt, source)
* `Listing` (channelId, priceTon/priceUsd, format="post", categories, constraints, active)
* `Request` (advertiserId, budget, niche, languages, minSubs/minViews, dates, brief)
* `Deal`

  * links: listingId OR requestId (и вторую сторону)
  * terms: price, format, publishAt, verificationWindow
  * `status` (см. ниже)
* `EscrowPayment` (dealId, depositAddress, expectedAmount, txHash, confirmedAt)
* `Creative` (dealId, text, mediaFileIds[], version, status)
* `DealEvent` (dealId, type, payload, createdAt) — для аудита/README

### Статусы сделки (пример)

`NEGOTIATING → TERMS_LOCKED → AWAITING_PAYMENT → FUNDED → CREATIVE_DRAFT → CREATIVE_REVIEW → APPROVED → SCHEDULED → POSTED → VERIFYING → RELEASED | REFUNDED | CANCELED`

## 4) Главные user-flows (как это должно работать)

### Flow 1: Владелец создаёт listing

1. В мини-аппе: “Добавить канал” → инструкция “добавь бота админом”
2. Бот проверяет, что он в канале и имеет нужные права (и что пользователь — админ канала)
3. Backend подтягивает/обновляет stats
4. В мини-аппе: задать цену и условия → listing опубликован

**PR-менеджеры:** дать кнопку “Добавить менеджера”, но на критичных действиях (выплата/смена реквизитов/принятие сделки) — **повторно проверять**, что пользователь всё ещё админ канала или имеет нужные права.

### Flow 2: Рекламодатель создаёт request

1. В мини-аппе: “Создать заявку” (бриф + фильтры)
2. Владельцы каналов видят заявки, откликаются → создаётся “черновая” сделка

### Unified workflow (обязательно)

Не важно, откуда старт (listing или request) — дальше один и тот же процесс в боте:
переговоры → зафиксировать terms → оплатить → креатив → аппрув → автопост → верификация → release/refund.

## 5) “Verified stats”: как закрыть требование реально

### Вариант A (максимально “по-простому”, может быть недостаточно для “language/premium”)

* subscribers: Bot API/данные чата
* views/reach: **может быть ограничено**, зависит от доступности полей/методов в Bot API (в документации это не всегда покрывает “channel analytics”). (([core.telegram.org][1]))
* languages/premium: пометить как “недоступно через Bot API” и явно написать в limitations.

### Вариант B (самый “в лоб” под формулировку про графики/языки)

Использовать **Telegram client API stats.getBroadcastStats**, который отдаёт followers/views_per_post/languages_graph и т.п. (([core.telegram.org][2]))
Тогда тебе нужно продумать, **как авторизовать admin-аккаунт** для доступа к stats (например, отдельный сервисный аккаунт/TDLib). Для хакатона часто ок, если честно описать это в README.

Я бы делал так: **B как основной**, A как запасной деград-режим.

## 6) Автопостинг и проверка “не удалено/не изменено”

* Автопостинг: бот публикует в канал, сохраняешь `chat_id + message_id`. Боты получают channel_post/edited_channel_post апдейты в каналах, где они состоят, что удобно для детекта правок. (([core.telegram.org][1]))
* Проверка “не изменено”: слушаешь `edited_channel_post`, если прилетела правка по нужному `message_id` — ставишь флаг “tampered”.
* Проверка “не удалено”: делай периодический job, который пытается выполнить действие, зависящее от существования сообщения (например, copy/forward в лог-чат). Если падает — считаешь удалённым/недоступным.
* Выплата: только после `verificationWindow` (например 1–24 часа) “без tamper/delete”.

## 7) Эскроу на TON (MVP-уровень)

* На сделку создаёшь **уникальный depositAddress**.
* Мониторишь входящие транзакции и сумму.
* Как только подтверждено — `FUNDED`.
* После `RELEASED` отправляешь payout владельцу; после `REFUNDED` — назад рекламодателю.
* Обязательно: таймаут оплаты и авто-cancel.

(В README достаточно описать модель безопасности: hot wallet, ключи в env, отдельные адреса на сделки, audit trail.)

## 8) План работ (чтобы не утонуть)

### Этап 0 — каркас (быстро)

* repo + docker-compose (api, db, redis)
* бот webhook + miniapp auth (initData)
* базовая схема БД + миграции

### Этап 1 — маркетплейс

* Channel onboarding: “добавь бота админом” + проверка прав
* Listings CRUD (только format=post)
* Requests CRUD
* Поиск/фильтры (цена, subs, views, язык)

### Этап 2 — unified deal workflow (ядро)

* Создание сделки из listing↔request
* Бот-кнопки: принять/отклонить, предложить цену/дату, “зафиксировать terms”
* Таймауты + статусы + DealEvent лог

### Этап 3 — эскроу

* Генерация depositAddress
* Мониторинг оплаты → FUNDED
* Refund path + auto-cancel

### Этап 4 — креатив + аппрув + автопостинг

* Загрузка креатива через бота (text + media file_id)
* Аппрув/правки
* Планировщик публикации
* Пост-верификация → release/refund
