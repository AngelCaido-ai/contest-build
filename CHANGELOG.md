# История изменений

Формат записи: дата — изменение — причина/контекст.

## 2026-02-14
- Backend: извлечён shared service layer `deal_actions.py` из `deals.py` и `bot_actions.py`; ~750 строк дублированной бизнес-логики (7 операций: update_terms, update_status, create_creative, update_creative_status, get_creative, update_publish_at, add_advertiser_brief + constants и helpers) перенесены в единый модуль `app/services/deal_actions.py`; route handlers сжаты до 5–15 строк (auth + delegation + error mapping); `deals.py` сократился с 597 до 352 строк, `bot_actions.py` с 1122 до 871 строки; обновлён `docs/backend.md` — причина: каждое изменение бизнес-правила приходилось вносить дважды, расхождения между miniapp и bot API уже накопились.
- Backend: `set_status` в `deal_service.py` теперь enforce'ит допустимые переходы из `ALLOWED_TRANSITIONS`; при недопустимом переходе бросает `InvalidTransitionError(ValueError)`; caller-side проверки `can_transition` удалены из `deals.py` и `bot_actions.py`; `escrow_service.py` (`confirm_payment`, `release_payment`, `refund_payment`) при `InvalidTransitionError` логирует warning и возвращает payment (idempotent); `deal_tasks.py` при `InvalidTransitionError` логирует warning и пропускает сделку; дополнена таблица `ALLOWED_TRANSITIONS` (добавлены `TERMS_LOCKED→TERMS_LOCKED`, `FUNDED→CREATIVE_REVIEW/REFUNDED`, `CREATIVE_REVIEW→CREATIVE_DRAFT/CREATIVE_REVIEW`, `APPROVED→POSTED/VERIFYING`, `SCHEDULED→VERIFYING`); добавлен `test_deal_service.py`; обновлён `docs/backend.md` — причина: `set_status` не валидировал переходы, `can_transition` вызывался только в 2 из 12 мест, остальные caller'ы могли сделать любой переход.

## 2026-02-13
- Bot: FSM-storage заменён с `MemoryStorage` на `RedisStorage` (aiogram 3 built-in); добавлена настройка `redis_url` в `BotSettings` (default `redis://localhost:6379/1`); бот использует Redis DB 1 (RQ worker — DB 0) для изоляции ключей; `docker-compose.yml` — добавлен `REDIS_URL` в environment секцию bot; обновлены `docs/bot.md` и `.env.example` — причина: `MemoryStorage` терял все FSM-данные (черновики, активные сделки, flow-данные) при рестарте/деплое/крэше бота, критично для финансового бота с escrow.
- Bot/Watcher: заменён синхронный `requests` на асинхронный `httpx.AsyncClient` в `bot/app/services/api_client.py` и `watcher/app/handlers.py`; все 30+ методов `api_client` стали `async def`; создан singleton `httpx.AsyncClient` с `base_url`, `timeout=httpx.Timeout(10.0, connect=5.0)` и `headers`; lifecycle management — `init_client()` при старте, `close_client()` при остановке; все 71+ вызовов `api_client.*` в handlers (`deals.py`, `marketplace.py`, `start.py`, `onboarding.py`) обновлены на `await`; `_resolve_deal_role` стал `async def`; добавлен `httpx` в `requirements.txt`; обновлены `docs/bot.md` — причина: синхронный `requests` блокировал asyncio event loop aiogram на 200–2000 мс при каждом API-вызове, при недоступности backend бот зависал навсегда (timeout не установлен).
- Backend: `decrypt_deposit_key` в `ton_escrow.py` — убран silent fallback (`except Exception: return value`), заменён на `raise ValueError`; при невалидных данных, неверном ключе или повреждённом blob функция теперь бросает исключение вместо молчаливого возврата сырого input; удалён тест `test_decrypt_plain_fallback`, добавлены `test_decrypt_invalid_raises` и `test_decrypt_wrong_key_raises`; обновлён `docs/backend.md` — причина: уязвимость, при ошибке дешифровки `send_payout`/`send_refund`/`send_sweep` получали невалидную мнемонику, средства оставались заблокированы навсегда.
- Backend: эндпоинты `GET /listings/`, `GET /listings/{id}`, `GET /requests/`, `GET /requests/{id}` теперь требуют JWT-авторизацию (`Depends(get_current_user)`); `GET /listings/` заменён `get_optional_current_user` на `get_current_user`; добавлены bot-эндпоинты `GET /bot/listings`, `GET /bot/listings/{id}`, `GET /bot/requests`, `GET /bot/requests/{id}` с `Depends(get_bot_secret)`; бот переключён на bot-эндпоинты в `api_client.py`; miniapp `ListingsPage` и `RequestsPage` теперь показывают ошибку при 401 вместо пустого списка; обновлены `docs/backend.md` — причина: бюджеты, брифы, статистика каналов и `advertiser_id` были доступны анонимно через незащищённые read-эндпоинты.
- Backend: `verify_init_data` теперь валидирует поле `auth_date` из Telegram `init_data` — если отсутствует, не число или старше `INIT_DATA_MAX_AGE_SECONDS` (по умолчанию 300 сек), данные отклоняются; добавлена настройка `init_data_max_age_seconds` в `Settings`; обновлены `.env.example` и `docs/backend.md` — причина: replay attack, перехваченный `init_data` без проверки `auth_date` был валиден бессрочно.
- Backend: сравнение секретов (`bot_secret` в `deps.py`, HMAC-хеш в `security.py`) переведено с оператора `!=` на `hmac.compare_digest()` (constant-time) — причина: timing attack позволяла побайтово подобрать секрет, измеряя время ответа.
- Backend: scheduler — добавлена дедупликация задач: `job_id=task.__name__` гарантирует максимум 1 job на тип задачи в Redis; перед `enqueue` проверяется статус существующего job (`queued`/`started`/`scheduled` — пропуск); добавлен `job_timeout` для каждой задачи (30–120 сек) — зависшая задача убивается и job_id освобождается; `result_ttl=0` — результаты не хранятся; обновлена документация `docs/backend.md` — причина: без `job_id` каждые 20 сек создавались дубли, при длительных HTTP-задачах копились в очереди, при нескольких worker-ах — параллельное выполнение одной задачи и двойные финансовые операции.
- Backend: добавлена пессимистичная блокировка (`SELECT ... FOR UPDATE`) во все финансовые escrow-операции (`confirm_payment`, `release_payment`, `refund_payment`, `sweep_deposit`) и в `create_deposit_address`; фоновые задачи `check_verification_windows` и `sweep_completed_deposits` перечитывают строки с блокировкой перед вызовом; `scan_incoming_payments` блокирует строку после обнаружения транзакции; добавлен тест конкурентности (`test_concurrent_release_single_payout`); обновлена документация `docs/backend.md` — причина: race condition позволял двойную отправку TON при конкурентных запросах (read-then-write без блокировки строки в БД).
- Backend: убраны дефолтные значения `jwt_secret` и `bot_secret` в `Settings` — при отсутствии переменных приложение не запустится; добавлена startup-валидация (jwt_secret != "change_me", длина >= 32, bot_secret не пуст) — причина: критическая уязвимость, дефолт "change_me" позволял сформировать произвольный JWT.
- Backend: удалено поле `roles` из `AuthRequest` и `BotAuthRequest` — клиент больше не может задать произвольную роль при авторизации; новые пользователи всегда создаются с ролью `["advertiser"]` — причина: privilege escalation, любой пользователь мог отправить `{"roles": ["admin"]}` и получить произвольную роль.
- Bot: ввод даты/времени публикации заменён с ручного ISO-формата на inline-календарь с выбором дня, часа и минут; добавлена директория `bot/app/keyboards/` с модулем `calendar.py`; router календаря подключён в `main.py`; текстовый ввод сохранён как fallback с поддержкой формата `ДД.ММ ЧЧ:ММ` — причина: ISO-формат непригоден для пользователей, высокий процент ошибок ввода.
- Backend: добавлен эндпоинт `GET /deals/{id}/events` — возвращает историю событий сделки (новые первыми), доступ для участников сделки (owner/manager/advertiser) по JWT — причина: фронтенду нужен отдельный эндпоинт для ленивой загрузки истории событий на странице сделки.
- Miniapp: добавлен компонент `DealEventTimeline` — timeline с человеко-читаемыми названиями событий, цветными маркерами, форматированными payload-деталями и кнопкой «Показать все»; заменяет старый список raw JSON событий на странице сделки — причина: улучшение UX истории сделки.
- Backend: `telegram_service.py` — добавлен автоматический retry для всех запросов к Telegram Bot API: до 3 повторных попыток при transient-ошибках (429, 500, 502, 503, 504) с exponential backoff (1 с → 2 с → 4 с) и учётом заголовка `Retry-After`; добавлены таймауты (30 с / 60 с для загрузки файлов) — причина: одна неудачная отправка уведомления приводила к потере информации о статусе сделки.
- Backend: scheduler — каждый `queue.enqueue()` обёрнут в `try/except` с логированием; раньше одно исключение (например, Redis недоступен) останавливало весь цикл и все 6 фоновых задач — причина: повышение отказоустойчивости планировщика.
- Backend: добавлен `GET /health` — проверка доступности PostgreSQL и Redis; Docker Compose получил healthcheck для backend, все зависимые сервисы (caddy, worker, scheduler, bot, watcher) переведены на `service_healthy`; Caddy настроен на active health check upstream — причина: если FastAPI зависает без падения процесса, Docker и Caddy не могли обнаружить проблему.
- Backend: удалены escrow-эндпоинты `POST /escrow/deals/{id}/confirm`, `release`, `refund` — они были защищены только статическим `X-Bot-Secret`, но ни один внутренний сервис не вызывал их по HTTP; worker вызывает `escrow_service` напрямую. Удалены Pydantic-схемы `EscrowConfirmRequest`, `EscrowReleaseRequest`, `EscrowRefundRequest`. Тесты переведены на прямые вызовы сервисных функций. Обновлена документация `docs/backend.md`.
- Miniapp: добавлена обработка оффлайна — при потере сети показывается sticky-баннер «Нет подключения к интернету», при восстановлении — «Соединение восстановлено» (3 с); `apiFetch` бросает `NetworkError` вместо generic ошибки; `useApi` автоматически перезапрашивает данные при возврате сети; контент сдвигается под баннер.
- Miniapp: добавлен `ErrorBoundary` — необработанные исключения в компонентах больше не крашат всё приложение; пользователь видит экран с ошибкой и кнопкой «Попробовать снова» вместо белого экрана. Два уровня: глобальный (main.tsx) ловит ошибки провайдеров, маршрутный (Layout.tsx) ловит ошибки страниц с сохранением навигации.
