# История изменений

Формат записи: дата — изменение — причина/контекст.

## 2026-02-12
- Добавлена строгая валидация TON-адресов в `EscrowReleaseRequest.payout_address`, `EscrowRefundRequest.refund_address` и `UserWalletUpdate.linked_wallet`; невалидные значения теперь отклоняются на уровне Pydantic с `422` — причина: исключить сценарий, когда произвольная строка доходит до release/refund и приводит к риску потери средств.
- Вынесен общий валидатор `validate_ton_address` в `backend/app/utils/ton_address.py`, а `_normalize_address` в `ton_escrow.py` переведён на него без silent-fallback — причина: централизовать проверку адресов и убрать молчаливое принятие невалидных значений.
- Обновлены тесты `backend/tests/test_refund_api.py`: happy-path использует валидный TON-адрес, добавлены кейсы на `422` для невалидных `payout_address`/`refund_address` — причина: зафиксировать fail-fast поведение API.
- Обновлён `docs/backend.md` с явным описанием валидации TON-адресов в escrow и wallet endpoint’ах — причина: синхронизировать документацию с текущим контрактом API.

## 2026-02-11
- Добавлен фоллбэк для `views_per_post`: если `GetBroadcastStatsRequest` вернул 0 (нет постов за стат-период), считаем среднее из последних 20 постов канала — причина: Telegram отдаёт среднее за 7 дней, каналы без новых постов получали 0.
- Добавлено логирование в `stats_service` (MTProto + Bot API fallback) и эндпоинт `refresh_stats` — причина: ошибки Telethon поглощались молча, невозможно было понять почему `views_per_post` = null.
- В miniapp `ChannelsPage` после обновления статистики (`refreshStats`) вызывается `refetch()` — причина: данные на странице не обновлялись после нажатия «Обновить», нужно было перезайти.
- Добавлен sweep остатков escrow: после release/refund фоновая задача отправляет остаток (неиспользованный reserve) рекламодателю с `send_mode=128`; добавлены поля `sweep_tx_hash`, `swept_at`, миграция `0006_sweep_fields` и настройки `SWEEP_DELAY_MINUTES`, `SWEEP_MIN_BALANCE_TON` — причина: не оставлять средства на deposit-кошельках после завершения сделки.
- Исправлен дубль сообщения при выборе сделки в боте: при `set_active=True` теперь отправляется только закреплённое сообщение «Активная сделка», а не два сообщения — причина: `_send_deal_details` отправляла обычное сообщение, а затем `_update_active_deal_pin` отправляла ещё одно с заголовком.
- Команда `/start` в боте теперь обрабатывает deep link параметр `deal_{id}`: при переходе из Mini App сделка автоматически становится активной в чате — причина: кнопка «Перейти в бота» должна не просто открывать бота, а активировать конкретную сделку.
- Добавлена проверка активной сделки при создании сделки по листингу (`POST /deals/`, `POST /bot/deals`): если по листингу уже есть сделка не в финальном статусе (CANCELED/RELEASED/REFUNDED), возвращается 409 Conflict — причина: исключить дублирование активных сделок по одному листингу.
- Добавлен фильтр `exclude_own` в `GET /listings`: при `exclude_own=true` и JWT ответ исключает листинги каналов текущего пользователя — причина: убрать self-отклик на свои размещения в каталоге Mini App.
- В каталоге Mini App (`/listings`) включён запрос с `exclude_own=true` — причина: пользователь сразу видит только чужие листинги для отклика.
- `GET /listings/{id}` теперь возвращает preview канала и статистику (если есть) — причина: отображать предпросмотр листинга в Mini App до создания сделки.
- В Mini App добавлен экран предпросмотра листинга и перенесено создание сделки с каталога на этот экран — причина: пользователь должен видеть условия и статистику перед откликом.
- `GET /channels/` и `GET /channels/{id}` теперь возвращают поле `stats` (если сохранено) — причина: показывать статистику выбранного канала в предпросмотре заявки.
- В Mini App добавлен экран предпросмотра заявки (Request) с выбором канала, статистикой и откликом — причина: не создавать сделку до просмотра условий заявки.
- Создан `deploy.py` — скрипт деплоя на сервер через SSH/SFTP — причина: автоматизация загрузки файлов, пересборки контейнеров и проверки статуса.
- Создан `docs/deploy.md` — инструкция по деплою — причина: документирование архитектуры на сервере, вариантов деплоя и отката.
- Исправлен `GET /channels/`: менеджеры теперь видят назначенные каналы (OR по `channel_managers`) — причина: менеджер не видел своих каналов в miniapp.
- Исправлен `GET /channels/{id}`: доступ разрешён менеджерам — причина: менеджер получал 404 при открытии назначенного канала.
- Исправлен `POST /stats/channels/{id}/refresh`: доступ разрешён менеджерам — причина: менеджер не мог обновить статистику назначенного канала.
- В miniapp секция управления менеджерами скрыта для не-владельцев — причина: менеджер не должен видеть/редактировать список менеджеров.
- `GET /deals/{id}` расширен: добавлены `channel_info` (title/username + stats), `advertiser_info` и `events` — причина: на детальном экране сделки нужно больше контекста без дополнительных запросов.
- В miniapp экран сделки расширен: добавлены секции по каналу, датам, верификации и истории событий — причина: детальный экран сделки показывал слишком мало информации.
- В JWT API добавлены endpoint’ы управления сделкой (`/deals/{id}/terms`, `/publish_at`, `/status`, `/creative`, `/creative/status`, `/creative GET`, `/advertiser_brief`) — причина: вынести ключевой workflow из bot-only API и дать miniapp полный контроль по сделке.
- В auth API добавлены `GET /auth/me` и `POST /auth/me/wallet` — причина: miniapp должен уметь управлять payout-кошельком без bot-secret endpoint’ов.
- В miniapp добавлены страницы: добавление канала, создание листинга, создание заявки, сохранение кошелька — причина: закрыть CRUD и онбординг из интерфейса miniapp.
- В miniapp экран сделки получил action-блоки по ролям (условия, статус, publish_at, креатив, ревью, advertiser brief, просмотр креатива) — причина: сделать end-to-end управление сделкой в miniapp без постоянного перехода в бота.
- В miniapp экран отклика на листинг и заявку расширен полями сделки (цена, формат, publish_at, verification_window, бриф) — причина: улучшить первичную коммуникацию и качество входящих сделок.
- Добавлен JWT endpoint `POST /deals/media/upload`: miniapp загружает реальный файл, backend отправляет его в Telegram и возвращает `file_id` — причина: убрать ручной ввод `media_file_ids` JSON.
- В miniapp вместо ISO-строк добавлен удобный выбор даты/времени (datetime-local + быстрые пресеты) в формах отклика и управления сделкой — причина: сократить ошибки ввода и ускорить сценарии.
- В miniapp в карточке сделки добавлен пошаговый мастер с прогрессом (`Шаг X из Y`, навигация Назад/Далее, переключение “показать все шаги”) — причина: сделать workflow последовательным и понятным для обеих ролей.
- В bot API добавлены endpoint’ы переписки по сделке: `POST /bot/deals/{id}/messages` и `GET /bot/deals/{id}/messages` с хранением сообщений в `DealEvent(type="MESSAGE")` — причина: реализовать переговоры в боте между сторонами.
- В `bot/deals.py` добавлены кнопки «Написать сообщение» и «История переписки», FSM `DealMessageState.content`, отправка текста/медиа и пагинация истории — причина: дать сторонам быстрый канал общения прямо из карточки сделки.
- В уведомлении о новом сообщении добавлены быстрые действия Open deal / Reply / History — причина: сократить путь до ответа и ускорить коммуникацию.
