Ниже — максимально практичный **план реализации эскроу на TON** для хакатон-MVP (и что можно улучшить “в прод”).

---

## 0) Выбор модели эскроу (2 варианта)

### Вариант A — Custodial (быстрее для MVP)

Ты реально **удерживаешь средства на своих кошельках** (по одному кошельку на сделку), а потом делаешь **release/refund** транзакциями с сервера.

**Плюсы:** быстро, понятно, легко дебажить.
**Минусы:** ты отвечаешь за ключи и безопасность.

### Вариант B — Smart-contract escrow (правильнее “в прод”)

Сделка живёт в смарт-контракте: оплата → контракт держит → контракт отправляет получателю/делает refund по условиям.

**Плюсы:** меньше доверия к серверу.
**Минусы:** дольше реализовывать и тестировать, больше рисков по багам.

Для хакатона почти всегда берут **Вариант A**, а в README пишут “future: move to contract escrow”.

## 1) Спецификация эскроу: статусы и правила

Минимальный state machine для escrow-части:

1. `AWAITING_PAYMENT` (создана, ждём депозит)
2. `FUNDED` (депозит пришёл и подтверждён)
3. `HELD` (средства удерживаются до автопоста + проверки)
4. `RELEASED` (выплата владельцу канала)
5. `REFUNDED` (возврат рекламодателю)
6. `CANCELED` (не оплатили вовремя / сделка отменена до фонда)

Таймауты:

* `payment_deadline` (например 30–60 мин)
* `approval_deadline` (если зависло на согласовании — refund)
* `verification_window` (после поста держим N минут/часов)

---

## 2) Стратегия кошельков: “отдельный адрес на сделку”

### Минимум (MVP)

На каждую сделку генерируешь **новую пару ключей** (wallet v4) → получаешь `depositAddress`.

Хранишь:

* `dealId`
* `depositAddress`
* `depositKeyEncrypted`
* `expectedAmountNano`
* `fundingTxHash/lt` (или аналогичный идентификатор)
* `status`

### Лучше (но можно позже)

HD-деривация от мастер-сида (как “дерево” адресов), чтобы не хранить много сидов. Но для MVP достаточно генерации ключей на сделку.

---

## 3) UX оплаты (Mini App)

На странице сделки показываешь:

* сумму (TON)
* адрес депозита
* кнопку **“Pay with TON”** через **TonConnect** (идеально)
* запасной вариант: “копировать адрес” (если без TonConnect)

Важно: сумму лучше фиксировать точно (например `1.234 TON`), а не “от”.

---

## 4) Мониторинг поступлений (детектор депозита)

Подход:

* сервис `escrow-watcher` (cron/queue каждые 3–10 секунд для активных сделок)
* источник данных: toncenter/tonapi (любая API, которая отдаёт транзакции адреса)

Алгоритм:

1. Берёшь `depositAddress`
2. Получаешь последние транзакции
3. Ищешь **входящий transfer**:

   * `amount >= expectedAmount` (или ровно, если строго)
   * (опционально) `from == advertiserWallet` если он известен
4. Ставишь `FUNDED`, сохраняешь уникальный id транзакции (hash + lt)
5. Делаешь **идемпотентность**: повторная обработка той же tx ничего не ломает

Про “подтверждения”: на TON финальность быстрая, но для спокойствия можно ждать 1–2 “шага” обновления (или просто 10–20 секунд) перед переводом статуса.

---

## 5) Удержание средств (HELD)

После `FUNDED` ты **не трогаешь** деньги, пока не выполнится:

* креатив `APPROVED`
* наступило `publishAt`
* автопост прошёл
* проверка “не удалено/не отредактировано” выдержана `verification_window`

---

## 6) Release (выплата владельцу)

Когда условия выполнены:

1. Считаешь:

   * `payout = dealAmount - platformFee - networkReserve`
2. С `depositWallet` отправляешь:

   * `payout` на `ownerPayoutAddress`
   * (если fee отдельным переводом) `platformFee` на `feeWallet`
3. Сохраняешь `payoutTxHash`, статус `RELEASED`

**Важно про комиссии:** у кошелька должны остаться копейки на комиссии, иначе payout может зафейлиться. Поэтому держи `networkReserve` (например 0.02 TON) или делай “send all but keep X”.

---

## 7) Refund (возврат рекламодателю)

Триггеры refund:

* истёк `approval_deadline`
* владелец отклонил после фонда
* автопост не состоялся
* пост удалён/изменён в verification window

Механика та же, что payout:

* перевод с `depositWallet` обратно на `advertiserRefundAddress`
* `REFUNDED` + `refundTxHash`

---

## 8) Key management и безопасность (чтобы не утонуть)

Минимальные правила:

* **никогда не логируй** seed/private key
* ключи в БД — **только зашифрованные** (AES-GCM), master-key в env/secret manager
* отдельный сервис/роль, который имеет право **подписывать** транзакции (не весь backend)
* rate limit на release/refund
* `DealEvent`-аудит: кто и когда нажал кнопку/какой переход статуса
* повторно проверяй права админа канала перед “release” (как требуют в спеках)

## 10) План по шагам (реально “сделать”)

1. **Сделка и статусы**: добавить escrow-поля и дедлайны
2. **Генерация deposit wallet** на создание сделки
3. **Экран оплаты** в mini app + TonConnect (или копировать адрес)
4. **Watcher**: поиск входящего депозита → `FUNDED`
5. **Флоу release/refund**: подписать и отправить транзакции, сохранить tx id
6. **Таймауты**: автокэнсел “не оплатили”, автосрыв “зависло”
7. **E2E тесты** на testnet: депозит → автопост mock → release / refund
